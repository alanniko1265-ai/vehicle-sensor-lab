# VehicleSensorLab 架构草案

## 1. 为什么先做虚拟传感器

第一阶段使用内核定时产生的模拟事件，目的是把以下问题分开：

- 驱动接口是否正确；
- 用户态是否能正确读取；
- 并发和缓冲是否正确；
- 真实引脚、设备树和传感器是否正确。

如果一开始同时接真实硬件，出现错误时很难判断问题属于硬件、设备树、驱动还是应用。

## 2. 模块边界

### 内核驱动负责

- 产生或接收传感器事件；
- 保存尚未被读取的事件；
- 实现 `open/read/poll/unlocked_ioctl/release`；
- 维护序列号、丢失数量和队列状态；
- 唤醒等待数据的进程；
- 校验来自用户态的控制参数。

### 用户态服务负责

- 打开和配置设备；
- 使用 `poll` 等待事件；
- 将内核事件转换为业务状态；
- 维护车辆状态机和故障规则；
- 向 CLI/Qt 客户端发布状态；
- 记录、回放和展示。

### Qt/CLI 不负责

- 直接解释内核内部状态；
- 在 UI 线程中阻塞读取设备；
- 决定驱动资源生命周期；
- 绕过服务直接操作多个底层接口。

## 3. 第一版事件模型：先思考，再编码

第一版事件至少需要表达：

- 事件类型：速度、温度、碰撞；
- 数值；
- 单调时钟时间戳；
- 递增序列号；
- 状态标志；
- 为后续兼容保留的字段。

请先回答：

1. 为什么 UAPI 中应使用固定宽度整数，而不是 `int`、`long`？
2. 为什么驱动与用户态共享的结构体不能随意改变字段顺序？
3. 读取接口一次返回一个事件还是一批事件？第一版为什么？
4. 没有事件时，阻塞打开和 `O_NONBLOCK` 打开分别应返回什么行为？
5. `read` 缓冲区小于一个完整事件时，是截断还是返回错误？
6. 多个进程同时读取时，是竞争同一事件队列，还是每个读者拥有副本？

第一阶段采用最简单且可解释的语义：**全局单队列，一次读取一个完整事件，多个读者竞争消费。** 后续再讨论广播模型。

## 4. 计划中的数据流

```text
内核定时器/按键中断
        ↓
事件构造与序列号
        ↓
有界环形缓冲区
        ↓ wake_up
read/poll/ioctl
        ↓
用户态采集线程
        ↓
车辆状态机
        ├── CLI/Qt
        └── 事件记录器
```

## 5. 暂时不做的内容

- 不在内核中实现业务故障规则；
- 不在内核中写文件或进行网络通信；
- 不修改正式设备树；
- 不使用 `mmap` 传输小型传感器事件；
- 不为了“高级”而加入无锁队列；
- 不在第一版实现多读者广播。

这些约束是为了保持驱动职责清晰，而不是因为相关技术永远不用学习。
